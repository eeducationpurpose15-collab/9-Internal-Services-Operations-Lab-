# Internal Services Operations Lab — сопровождение внутренних сервисов

## Цель проекта

**Сопровождать внутренние сервисы компании, автоматизировать их развёртывание и контролировать работоспособность**.

Самостоятельно создать небольшой внутренний сервис на FastAPI, организовать проект в Git, подготовить виртуальную машину, контейнеризировать сервис с помощью Docker, автоматизировать конфигурацию через Ansible, настроить GitLab и GitLab Runner, а затем организовать мониторинг сервиса с помощью Prometheus и Grafana.

Проект использует только темы, непосредственно присутствующие в рабочей программе: Git, GitLab/GitLab Runner, FastAPI/Postman, VM/Docker, Kubernetes, Ansible, Prometheus и Grafana. 

**Исходные условия:** у преподавателя и студентов нет готового приложения, репозитория, Dockerfile, виртуальной машины, Ansible-конфигурации, GitLab CI-конфигурации или готового мониторинга. Все необходимые файлы и настройки создаются по ходу выполнения проекта.

**Формат реализации:** внутренний сервис создаётся на FastAPI и первоначально запускается в Docker на виртуальной машине. Для практики Kubernetes и мониторинга используется Minikube. GitLab Runner выполняет автоматизированные задания проекта.

**Интернет:** необходим для первоначальной установки программ, получения Docker-образов и зависимостей. При использовании внешнего GitLab интернет также требуется для работы с репозиторием и CI/CD.

**Ограничение ресурсов:** на слабых компьютерах компоненты можно запускать последовательно. Наиболее ресурсоёмкие компоненты допускается выполнять на одной выделенной виртуальной машине учебной группы.

**Ограничение содержания:** в проект не включаются самостоятельные упражнения по `load average`, inode, состоянию процессов `D`, disk I/O, `free/available` и Linux permissions, поскольку эти вопросы присутствовали в собеседовании, но как отдельные темы данной рабочей программы не указаны.

Также не включаются Kafka/HAProxy, DataLake/DataWarehouse/S3, Terraform и Helm/HPA: они есть в рабочей программе, однако из предоставленного интервью не следует, что они являлись основной потребностью работодателя для данной позиции.

**Статус:** описание проекта для реализации. Команды, конфигурации и сценарии создаются и проверяются непосредственно в ходе выполнения.

# Этапы выполнения

**Порядок обучения:** Git → FastAPI → Postman → VM → Docker → Ansible → GitLab Runner → автоматизация → Kubernetes/Minikube → Prometheus → Grafana → проверка сопровождения.

Каждый этап содержит небольшое действие и проверяемый результат.

## 1. 🟢 Организовать проект в Git

**Соответствие: П.З.1 — «Git. Организация проекта».** 

Создать папку проекта.

Создать:

1. `README.md`;
2. каталог приложения;
3. каталог конфигураций;
4. `.gitignore`.

Инициализировать Git, добавить файлы и выполнить первый commit.

**Проверка:** файлы находятся под контролем Git, история содержит первый commit.

*Скриншот 1: структура проекта и история Git.*

---

## 2. 🟢 Создать внутренний сервис FastAPI

**Соответствие: П.З.3 — «FastAPI, Postman, интеграции».** 

Создать минимальный внутренний сервис.

Реализовать:

* `/` — информация о сервисе;
* `/health` — проверка работоспособности.

Запустить приложение.

**Проверка:** FastAPI запускается и отвечает на HTTP-запрос.

*Скриншот 2: работающий FastAPI.*

---

## 3. 🟢 Проверить сервис через Postman

**Соответствие: П.З.3 — «FastAPI, Postman, интеграции».**

Создать в Postman запросы:

1. `GET /`;
2. `GET /health`.

Проверить HTTP-коды и содержимое ответов.

**Проверка:** оба запроса выполняются успешно.

*Скриншот 3: успешный запрос Postman.*

---

## 4. 🟢 Подготовить виртуальную машину

**Соответствие: П.З.6 — «VM, Docker, LXC-контейнеры».** 

Создать учебную виртуальную машину.

Проверить:

1. запуск операционной системы;
2. сетевое подключение;
3. доступ к VM;
4. возможность запуска необходимых инструментов.

**Проверка:** виртуальная машина работает и доступна.

*Скриншот 4: работающая VM.*

---

## 5. 🟢 Контейнеризировать FastAPI

**Соответствие: П.З.6 — «VM, Docker, LXC-контейнеры».**

Создать `Dockerfile`.

Собрать Docker-образ приложения.

Запустить контейнер и открыть FastAPI.

Проверить:

`GET /health`

**Проверка:** внутренний сервис работает внутри Docker.

*Скриншот 5: запущенный контейнер и работающий `/health`.*

---

## 6. 🟡 Автоматизировать конфигурацию через Ansible

**Соответствие: П.З.8 — «Ansible, Puppet».** 

Создать:

* Ansible inventory;
* минимальный playbook.

Автоматизировать необходимые для стенда операции подготовки окружения.

Выполнить playbook на учебной VM.

Повторить выполнение и проверить результат.

**Проверка:** Ansible успешно применяет конфигурацию, после чего сервис может работать.

*Скриншот 6: успешное выполнение Ansible.*

---

## 7. 🟡 Развернуть GitLab и GitLab Runner

**Соответствие: П.З.2 — «Развёртывание GitLab и GitLab Runner на виртуальной машине».** 

Развернуть GitLab и GitLab Runner.

Создать проект.

Подключить Runner к проекту.

Создать минимальное тестовое задание.

**Проверка:** Runner получает и успешно выполняет задание.

*Скриншот 7: подключённый GitLab Runner.*

---

## 8. 🟡 Автоматизировать сборку и проверку FastAPI

**Соответствие: П.З.2 + лекция 1.2 «Платформы непрерывной интеграции и доставки».** 

Создать `.gitlab-ci.yml`.

Организовать простой процесс:

**Git → GitLab → GitLab Runner → сборка → проверка FastAPI.**

После изменения проекта pipeline должен автоматически выполнить предусмотренную проверку.

**Проверка:** pipeline завершается успешно.

*Скриншот 8: успешный pipeline.*

---

## 9. 🟡 Запустить Kubernetes в Minikube

**Соответствие: П.З.7 — «Kubernetes».** 

Установить и запустить Minikube.

Проверить:

1. состояние среды;
2. доступность Kubernetes;
3. возможность запуска учебной нагрузки.

Minikube далее используется для П.З.12 и П.З.13, которые непосредственно предусматривают Prometheus и мониторинг FastAPI в Minikube. 

**Проверка:** Kubernetes в Minikube работает.

*Скриншот 9: работающий Minikube.*

---

## 10. 🟠 Подготовить FastAPI для мониторинга в Minikube

**Соответствие: П.З.3 + П.З.7 + П.З.13.**

Разместить учебный FastAPI-сервис в среде, используемой для последующего мониторинга.

Проверить доступность приложения.

**Проверка:** FastAPI работает в учебной Kubernetes-среде.

*Скриншот 10: работающий FastAPI в Minikube.*

---

## 11. 🟠 Настроить Prometheus

**Соответствие: П.З.12 — «Prometheus в Minikube».** 

Развернуть Prometheus в Minikube.

Настроить получение доступных метрик учебного приложения.

Проверить поступление данных.

В лекционной части программы также непосредственно предусмотрен мониторинг метрик и алертинг с использованием Prometheus. 

**Проверка:** Prometheus получает метрики.

*Скриншот 11: данные в Prometheus.*

---

## 12. 🟠 Настроить Grafana

**Соответствие: П.З.13 — «Grafana (мониторинг FastAPI в Minikube)».** 

Подключить Grafana к источнику данных мониторинга.

Создать минимальную панель мониторинга FastAPI.

Отобразить доступные показатели состояния сервиса.

**Проверка:** Grafana отображает данные FastAPI.

*Скриншот 12: мониторинг FastAPI в Grafana.*

---

## 13. 🟠 Проверить сопровождение внутреннего сервиса

**Соответствие: П.З.12 + П.З.13 — Prometheus и Grafana.**

Остановить учебный FastAPI-сервис.

Проверить изменение наблюдаемого состояния.

Затем:

1. восстановить сервис;
2. проверить `/health`;
3. проверить Prometheus;
4. проверить Grafana.

Таким образом моделируется основная задача работодателя — сопровождение внутреннего сервиса — исключительно средствами, которые присутствуют в рабочей программе.

**Проверка:** изменение состояния обнаруживается мониторингом, а после восстановления FastAPI снова доступен.

*Скриншот 13: состояние сервиса до и после восстановления.*

---

## 14. Зафиксировать результат

**Соответствие: П.З.1 — «Git. Организация проекта».**

Собрать в Git-репозитории:

* Ansible inventory;
* Ansible playbook;
* `.gitlab-ci.yml`;
* необходимые Kubernetes-файлы;
* конфигурацию Prometheus;
* конфигурацию Grafana;
* инструкции запуска.

Для каждого этапа использовать формат:

**Задача → действия → проверка → фактический результат.**

В README разделить выполненные и невыполненные этапы.

**Проверка:** другой студент может воспроизвести проект по сохранённым файлам и инструкции.

*Скриншот 14: структура итогового репозитория.*

## Критерий завершения проекта

Проект считается выполненным, когда **с нуля создан внутренний FastAPI-сервис, проект организован в Git, сервис работает в Docker, конфигурация автоматизирована через Ansible, GitLab Runner выполняет автоматизированную проверку, сервис запущен в учебной Kubernetes-среде, Prometheus получает данные, Grafana отображает состояние FastAPI, а остановка и последующее восстановление сервиса подтверждаются мониторингом**.

> **Сопровождение внутреннего сервиса: развёртывание, автоматизация и мониторинг его работоспособности.**

Это наиболее узкое пересечение **главной потребности работодателя** и **П.З.1, П.З.2, П.З.3, П.З.6, П.З.7, П.З.8, П.З.12 и П.З.13 рабочей программы**.
